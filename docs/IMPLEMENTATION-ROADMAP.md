## Phase 3 — T12 self-tuning anomaly-threshold proposal `[x]` VERIFIED 2026-09-05 (not yet deployed — see gate below)

**0. Pre-existing security/quality gap closed first (prerequisite for T12, not T12 itself).** The `dd614ac` merge (commit `aad36af`) had shipped three tunnel-isolation features — FRP webhook gatekeeper, auto-sync tunnel origins, dynamic rate limiter — with zero tests. Wrote 44 tests derived from the actual implementation (`test_frp_webhook_gatekeeper.py` 17, `test_auto_sync_tunnel_origins.py` 7, `test_dynamic_rate_limiter.py` 19, 1 marked `xfail(strict=True)`) covering valid/invalid auth, replay, unauthorized/cross-tenant origin registration, malformed payloads, fail-closed behavior, create/update/delete/duplicate/stale events, tenant isolation, normal/threshold/burst/reset rate-limit behavior. This surfaced **two CRITICAL cross-tenant vulnerabilities**, both fixed with RED-before/GREEN-after tests in commit `6d0b441`:
  - **FRP webhook domain hijack**: `frp_webhook_gatekeeper`'s NewProxy handler checked only `RESERVED_SUBDOMAINS`, never that the domain matched what a JWT was actually issued for. A token minted for `alice.example.com` could register a proxy for `bob.example.com`. Fixed: extract identity the same way Login does, enforce `payload["domain"] == target_domain` for JWT clients, reject with `"Token is not authorized for this domain"` on mismatch.
  - **Auto-sync cross-tenant origin claiming**: `auto_sync_tunnel_origins` created a new origin for any unclaimed domain/tunnel-name string without checking whether another tenant already owned a matching origin by label/IP/tunnel-name substring. Fixed: scan all origins first, skip auto-creation when `already_claimed_by_someone_else`.
  - Also hardened the webhook's default fallback from `{"reject": False}` to `{"reject": True, ...}` for unrecognised FRP plugin ops (fail-closed, not fail-open).

**1. T12 proposal system implemented, commit `e59be16`.** `services/threshold_proposal_service.py` (pure `generate_threshold_proposal()` + `ThresholdProposalStore`) and `api/threshold_proposals.py` (admin-gated generate/approve/reject/rollback, viewer-readable list/get), mounted in `main.py`. Design constraints from the task, and how each is met:
  - *Never auto-converts recommendations into blocks*: `create()` only ever writes `status="pending"`; `SettingsService.update_settings()` is called nowhere except inside `approve()`/`rollback()`, both `require_admin`-gated at the API layer. Verified by both `test_threshold_proposal_store.py` (11 tests) and `test_threshold_proposal_api.py` (11 tests, RBAC boundary re-exercised at the HTTP layer, not just the service).
  - *Single origin cannot influence another origin's security profile / preserve per-origin isolation*: the threshold is confirmed (by reading `settings_service.py` and the `modsecurity.d` template) to be **one global value with no per-origin lever** — so the safety property this module actually enforces is refusing to let one origin's evidence drive a change that affects every other origin. A proposal requires `MIN_ORIGINS_FOR_CONSENSUS = 2` independently-sampled, independently-elevated origins; the reason string generated for every proposal explicitly states "This threshold is GLOBAL -- it will apply to every origin behind this WAF instance, not only the ones cited as evidence." This is a documented architectural limitation, not a per-origin isolation guarantee — there is no code path in this system that *could* scope a threshold change to one origin, because the WAF itself has no such mechanism to target.
  - *Insufficient/noisy data must not cause unsafe changes*: `MIN_SAMPLES_PER_ORIGIN = 200` excludes low-sample origins from consensus entirely (still shown in evidence for transparency, never counted toward the trigger). Tested directly in `test_threshold_proposal_service.py`.
  - *False-positive amplification / poisoned-log influence*: covered by the same consensus + sample-size gates — a single poisoned origin cannot clear `MIN_ORIGINS_FOR_CONSENSUS` alone, and the blended trigger percentage only sums across corroborating (already-elevated, already-sufficiently-sampled) origins, so a non-elevated or excluded origin's data never pulls the blended number. `test_threshold_proposal_service.py` includes a case asserting a single anomalous origin alone does not produce a proposal.
  - *Rollback/versioning*: `approve()` captures `previous_threshold` from `settings_service.get_settings()` **at approval time**, not from the proposal's own stale generation-time snapshot — so `rollback()` restores what was actually live, correct even if the setting changed between generation and approval. Tested explicitly.
  - *Shadow/simulation before activation*: **partially met, with a documented limitation.** `generate_threshold_proposal()` itself is pure and non-mutating (a "shadow" evaluation against read-only ClickHouse data) and nothing reaches production until an explicit admin `/approve`. A true forward-simulation ("what would the new threshold have blocked/allowed on historical traffic") is **not implemented** — ClickHouse's `access_logs` table does not log the raw per-request anomaly score, only the final status code, so there is no data to replay a hypothetical threshold against. This is a real gap, not a design choice; closing it would require adding anomaly-score logging to the ModSecurity→ClickHouse pipeline, out of scope for this phase.
